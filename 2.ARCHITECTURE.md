# AI-Based Document Classification System
# Software Architecture

Version: 1.0

---

# 1. Purpose

This document defines the complete software architecture for the AI-Based Document Classification System.

It specifies how the project is organized, how modules communicate, and how future features must integrate into the existing codebase.

This document is intended for both human developers and AI coding assistants.

Whenever implementation decisions conflict with generated code, this architecture document takes precedence.

---

# 2. Architecture Goals

The architecture is designed around five principles.

## Simplicity

The project should be understandable by beginner developers.

Avoid unnecessary abstractions.

---

## Modularity

Each module performs one responsibility.

Modules communicate through clearly defined interfaces.

---

## Maintainability

Every feature should be replaceable without affecting unrelated modules.

---

## Scalability

Future integrations such as Milvus, OpenAI, OCR or Authentication should require minimal changes.

---

## Readability

Readable code is preferred over clever code.

# 5. Backend Request Lifecycle

Every request follows the same path.

```

Browser

↓

Route

↓

Controller

↓

Service

↓

Utility / External Service

↓

Controller

↓

Browser

```

The request lifecycle must never change.

---

# 6. Layer Responsibilities

## Layer 1

Routes

Purpose

Receive HTTP requests.

Responsibilities

- Define endpoints
- Call controllers
- Return responses

Forbidden

- Business logic
- File processing
- AI calls

---

## Layer 2

Controllers

Purpose

Coordinate application logic.

Responsibilities

- Validate request
- Call services
- Build response

Forbidden

- Milvus queries
- OpenAI calls
- File parsing

---

## Layer 3

Services

Purpose

Business logic.

Examples

Upload Service

Embedding Service

Milvus Service

Classification Service

Text Extraction Service

Services may communicate with external systems.

---

## Layer 4

Utilities

Purpose

Reusable helper functions.

Examples

Text Cleaner

Prompt Builder

Filename Helper

Time Formatter

Utilities should not know anything about Express.

---

## Layer 5

External Services

Examples

Milvus

OpenAI

Local File System

Future Database

# 11. Text Processing Pipeline

Uploaded File

↓

PDF Parser

or

DOCX Parser

↓

Raw Text

↓

Cleaning

↓

Normalized Text

↓

Embedding

The cleaned text is the only version that should continue through the system.

---

# 12. Embedding Pipeline

Normalized Text

↓

Embedding Model

↓

Vector

↓

Milvus

The embedding service should never know how Milvus works.

It only generates vectors.

---

# 13. Milvus Pipeline

Embedding Vector

↓

Similarity Search

↓

Top 3 Matches

↓

Return Metadata

Milvus never decides classifications.

It only retrieves similar records.

---

# 14. Classification Pipeline

↓

↓

# 16. API Philosophy

Every endpoint should:

Accept JSON or multipart form data.

Return JSON.

Use proper HTTP status codes.

Never expose stack traces.

Use consistent response formatting.

---

# 17. Error Flow

Every error should follow the same path.

```

Exception

↓

Service

↓

Controller

↓

Error Middleware

↓

JSON Response

```

The server should never terminate because of user input.

---

# 18. Future Expansion

The architecture intentionally supports future integration with:

- OCR
- Authentication
- PostgreSQL
- MongoDB
- Background Job Queues
- Docker
- Cloud Deployment

Adding these features should require minimal changes to existing modules.

---

# 19. Architectural Constraints

The following constraints must always be respected.

- One responsibility per module.
- One responsibility per file.
- No circular dependencies.
- No duplicated business logic.
- No direct OpenAI calls from routes.
- No direct Milvus calls from routes.
- No HTML generation in services.
- No business logic in middleware.
- Keep frontend independent from backend implementation details.

---

# 20. Architecture Summary

The architecture is intentionally simple.

It follows:

Browser

↓

Express

↓

Controller

↓


Service

↓

External System

Each layer exists for one reason only.

Maintaining this separation will make the project easier to develop, debug, test and extend throughout the internship.
