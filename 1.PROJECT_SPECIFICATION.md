# 3. Project Overview

The system automatically classifies uploaded digital documents according to the Library of Virginia (LVA) Record Management Schedule.

Instead of relying on traditional keyword matching, the application uses semantic search powered by vector embeddings and Milvus.

The retrieved record candidates are then evaluated by a Large Language Model (LLM) using Retrieval-Augmented Generation (RAG) to determine the most appropriate record series.

The system returns:

- Schedule Title
- Schedule Number
- Series Title
- Series Number
- Retention Period
- Disposition Method
- AI Reasoning

---

# 4. Business Problem

Government organizations manually classify thousands of documents into predefined record schedules.

Manual classification suffers from:

- Human error
- Inconsistent categorization
- Slow processing
- Poor scalability

The objective of this project is to automate that classification process while maintaining understandable reasoning for every decision.

---

# 5. Project Objectives

The completed system shall be capable of:

- Uploading supported documents.
- Extracting readable text.
- Cleaning extracted text.
- Generating semantic embeddings.
- Searching Milvus using vector similarity.
- Retrieving the Top 3 LVA record candidates.
- Building a Retrieval-Augmented prompt.
- Sending the prompt to an AI model.
- Returning the best record classification.
- Explaining why that classification was selected.

# 7. Functional Requirements

## FR-1 Document Upload

The system shall allow users to upload documents.

Supported file types:

- PDF (.pdf)
- Microsoft Word (.docx)

Maximum upload size:

20 MB

Uploaded files shall be temporarily stored inside:

uploads/

---

## FR-2 Text Extraction

The system shall extract readable text from uploaded documents.

Supported extraction libraries:

PDF

- pdf-parse

Word

- mammoth

Extraction shall return plain UTF-8 text.

---

## FR-3 Text Cleaning

Before AI processing, extracted text shall be cleaned.

Cleaning includes:

- Removing duplicate spaces
- Removing blank lines
- Normalizing whitespace
- Removing formatting artifacts
- Trimming unnecessary characters

No semantic information should be removed.

---

## FR-4 Embedding Generation

The cleaned document text shall be converted into vector embeddings using an embedding model.

The embedding process must remain isolated inside the Embedding Service.

No other module should directly generate embeddings.

---

## FR-5 Milvus Search

The application shall query Milvus using the generated document vector.

The search should return:

Top 3 most similar LVA record series.

Returned metadata shall include:

- Schedule Title
- Schedule Number
- Series Title
- Series Number
- Series Description
- Retention Period
- Disposition Method

---

## FR-6 RAG Classification

The system shall construct a structured prompt containing:

- System instructions
- Extracted document text
- Top 3 Milvus candidates

The prompt shall be sent to an LLM.

The LLM shall return:

- Best Series Number
- Classification reasoning

No metadata should be invented by the model.

Metadata shall always originate from Milvus.

---

## FR-7 Metadata Mapping

The selected Series Number shall be mapped back to the complete metadata stored in Milvus.

The frontend should never depend on AI-generated metadata.

---

## FR-8 Result Display

The application shall display:

- Schedule Title
- Schedule Number
- Series Title
- Series Number
- Retention Period
- Disposition Method
- Classification Reasoning

The user should not need to understand AI terminology.

Results must be presented in a simple human-readable format.

# 11. Software Architecture Principles

The project shall follow a layered architecture with strict separation of concerns.

Each layer has one responsibility.

```
Client (Browser)
        │
        ▼
Routes
        │
        ▼
Controllers
        │
        ▼
Services
        │
        ▼
Utilities / External Services
        │
        ▼
Milvus / OpenAI / File System
```

No layer may bypass another layer.

For example:

❌ Route → Milvus

❌ Route → OpenAI

❌ Controller → Milvus

The correct flow is:

Route

↓

Controller

↓

Service

↓

Utility / External API

# 17. Error Handling Strategy

Every operation should fail gracefully.

Never crash the server because of user input.

Every API should return consistent JSON.

Example

Success

```json
{
    "success": true,
    "data": {}
}
```

Failure

```json
{
    "success": false,
    "message": "Only PDF and DOCX files are allowed."
}
```

Never expose stack traces to users.
