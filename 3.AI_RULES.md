# 21. AI Coding Assistant Rules (Antigravity IDE)

This project is intended to be developed with the assistance of an AI coding assistant. The assistant must follow the rules below throughout the entire development lifecycle.

## General Rules

1. Read the project documentation before implementing any feature.
2. Implement only the requested phase.
3. Never implement future phases unless explicitly instructed.
4. Never rewrite working code without a clear reason.
5. Never change the project architecture.
6. Never rename folders or files without approval.
7. Keep all code modular.
8. Prioritize readability over cleverness.
9. Generate beginner-friendly JavaScript.
10. Explain every newly created file after implementation.

---

## Technology Rules

The assistant shall use only the approved technology stack.

Allowed:

- Node.js
- Express
- HTML
- CSS
- Vanilla JavaScript
- Multer
- pdf-parse
- mammoth
- Milvus SDK
- OpenAI SDK
- dotenv
- cors
- morgan

Do not introduce additional frameworks unless requested.

Forbidden examples:

- React
- Angular
- Vue
- NestJS
- TypeScript
- Prisma
- Sequelize
- MongoDB
- Firebase

---

## Architecture Rules

Never violate the project architecture.

Correct flow:

Route

↓

Controller

↓

Service

↓

Utility / External API

Never:

- Call OpenAI directly from routes.
- Call Milvus directly from routes.
- Put business logic inside middleware.
- Put business logic inside routes.
- Put HTML generation inside services.

---

## Folder Rules

Create files only inside the appropriate folders.

Examples:

controllers/

Contains controllers only.

services/

Contains business logic only.

middleware/

Contains middleware only.

utils/

Contains reusable helper functions only.

Never mix responsibilities.

---

## Code Style Rules

Use:

- async / await
- const by default
- let only when necessary
- arrow functions where appropriate
- descriptive variable names

Avoid:

- callback nesting
- magic numbers
- duplicated logic
- deeply nested if statements

Maximum preferred function length:

50 lines

Maximum preferred file length:

300 lines

Split files if necessary.

---

## Dependency Rules

Before installing a new package, verify whether an existing dependency already solves the problem.

Never install unnecessary libraries.

Always prefer fewer dependencies.

---

## Comments

Comment only where the code benefits from explanation.

Do not comment obvious code.

Bad:

```js
// increment i
i++;
```

Good:

```js
// Remove page headers added by the PDF parser.
```

# 22. Development Workflow

Every feature should follow the same workflow.

Step 1

Understand the requirement.

↓

Step 2

Determine affected modules.

↓

Step 3

Implement backend.

↓

Step 4

Test backend.

↓

Step 5

Implement frontend.

↓

Step 6

Integrate frontend and backend.

↓

Step 7

Test complete feature.

↓

Step 8

Document changes.

No feature is complete until all eight steps are finished.

# 23. Feature Completion Checklist

A feature is considered complete only if:

- Code compiles successfully.
- Server starts without errors.
- Existing functionality still works.
- Feature is modular.
- Error handling is implemented.
- Input validation is implemented.
- Documentation is updated.
- No unnecessary files were created.
- No dead code remains.

# 24. Git Guidelines

Commit after completing each phase.

Example commit messages:

```
Initial Express project setup

Implement document upload endpoint

Add upload frontend

Implement text extraction

Integrate Milvus search

Implement RAG classification
```

Avoid commits such as:

```
fix

update

changes

working

test
```

Commit messages should describe completed work.

# 25. API Design Principles

Every endpoint must:

- Return JSON.
- Return appropriate HTTP status codes.
- Handle invalid requests gracefully.
- Validate input.
- Never expose internal errors.

Standard response format:

Success

```json
{
  "success": true,
  "message": "Operation completed successfully.",
  "data": {}
}
```

Failure

```json
{
  "success": false,
  "message": "Descriptive error message."
}
```

# 26. File Upload Standards

Accepted file types:

- .pdf
- .docx

Maximum size:

2 MB

Validation order:

1. File exists.
2. File size.
3. File type.
4. Safe filename.
5. Save to uploads/.

Reject invalid uploads immediately.

---

# 27. Performance Guidelines

Prefer simple solutions first.

Optimize only when profiling identifies a bottleneck.

Avoid premature optimization.

Target goals:

- Fast upload response
- Efficient text extraction
- Efficient Milvus search
- Minimal memory usage

Correctness takes priority over speed.

---

# 28. Error Handling Standards

Every service must:

- Catch expected errors.
- Throw meaningful exceptions.
- Log unexpected failures.
- Return user-friendly messages.

Users should never see stack traces.

---

# 29. Security Guidelines

Never trust user input.

Always validate:

- File type
- File size
- Request body
- Query parameters

Never commit:

- .env
- uploads/
- logs/
- API keys

All secrets must be stored in environment variables.

---

# 30. Phase Acceptance Criteria

A development phase is complete only if:

✓ Requirements implemented.

✓ Code reviewed.

✓ Server starts successfully.

✓ No console errors.

✓ Existing features remain functional.

✓ Documentation updated.

✓ Ready for the next phase.

---

# 31. Definition of Success

The project will be considered successful when a user can:

1. Open the web application.
2. Upload a PDF or DOCX document.
3. Have the system extract the document text.
4. Generate vector embeddings.
5. Search Milvus.
6. Retrieve the three most relevant LVA record series.
7. Use an LLM to determine the best classification.
8. View the final classification, metadata, and reasoning through the frontend.

At every stage, the system should remain modular, readable, maintainable, and easy to extend.
